# KORLIX Messenger companion authentication

Prepared October 24, 2026 (America/New_York). Ricardo approved public source upload and continued backend deployment on October 25. Both database migrations are applied and the backend runtime is live.

The independent Flutter app uses `/api/messenger/auth/{signin,signup,refresh,signout,password-reset}` and `/api/messenger/account/delete-request`. A strict POST-only alias invokes existing verified account handlers while retaining the original namespace for authorization. Older deployments return 404 rather than creating a hub device session.

Migration `20261025014426_korlix_messenger_app_sessions.sql` retains the deployed companion table and existing Receipt Wiz bindings, adds an immutable-at-registration `client_app`, scopes active installations by app, and adds a service-only Messenger registration RPC. Anonymous/authenticated clients cannot read the bindings or execute registration. Tokens remain provider-verified; user-editable metadata never grants a companion session or a higher device allowance. Revoked bindings remain to prevent fallback to legacy hub authentication. Messenger sessions can access Social and their account endpoints; receipt and AI generation endpoints are excluded even when a caller changes or omits the app header.

Accounts, profiles, connections, conversations and message receipts are shared with the hub. Sign-out revokes only the current provider login/binding. Account deletion remains a shared-account action with an explicit client warning. Independent app sessions inherit the existing per-plan companion device-limit rules; this change adds no pricing tier.

The compact conversation list adds `GET /api/social/messenger_inbox` and migration `20261025014427_korlix_messenger_inbox.sql`. Its service-only invoker RPC returns accepted conversations ordered by latest visible message, server-side unread/search filters, last-message timestamps, sender direction and safe attachment preview metadata. It reuses the existing message-pair and unread indexes. Expired self/everyone dumps, deleted content, blocked peers, suspended profiles and private presence remain filtered. The original hub connection API is unchanged.
